# Technical Design 技术方案

基于当前代码仓库和用户明确需求，编写可落地的工程技术方案。

## 输出规则

- 除非用户要求其他语言，所有面向用户的输出和生成文档默认使用中文。
- 优先写入可长期维护的 Markdown 文档，而不是只在对话里回答。
- 默认路径：`docs/technical-design/{topic-slug}.md`。
- 如果用户指定路径，使用用户指定的精确路径。
- 产品需求、技术设计和任务拆分必须分开，不要把技术方案写成 PRD。
- 不要编造仓库事实。先读取相关代码、配置、文档、测试和已有设计记录。
- 如果业务规则、兼容性要求或运维约束不清楚，并且会实质影响方案，把问题记录到“待确认问题”，并在锁定方案前询问用户。

## 使用场景

适用于：

- 新功能技术方案。
- 重构或迁移设计。
- 架构方案和 RFC 风格文档。
- 重要技术决策的 ADR。
- 涉及外部服务、API、任务、数据存储或基础设施的集成方案。
- 需要风险、发布、测试和任务排序的实施计划。

不适用于：

- 纯 PRD 或产品需求写作。应使用 product 类技能。
- 只研究已有代码、没有提出变更方案。应使用 `code-research`。
- 代码审查发现问题。应使用 `code-review`。
- 用户要求直接修复的简单 bug，且不需要额外设计。

## 工作流

### 1. 明确范围

识别：

- 问题背景和期望结果。
- 范围内和范围外的工作。
- 受影响的用户或系统。
- 必需的行为变化。
- 非功能需求：性能、可靠性、安全、隐私、成本、兼容性、可观测性。

如果请求较宽泛，先给出简洁的范围摘要，然后基于合理假设继续。只有缺失信息会阻碍安全设计时才询问用户。

### 2. 读取当前系统

读取足够的真实项目上下文，让方案可实现：

- README、架构文档、AGENTS/CLAUDE 指令。
- 相关模块、API、schema、配置、任务、测试和部署文件。
- 路由、持久化、认证、后台任务、错误处理、日志、功能开关等既有模式。
- 仓库中相似实现。

把已验证事实和假设分开记录。

### 3. 选择方案形态

当存在多个可行路径时，做简洁、面向决策的对比：

- 方案。
- 工作方式。
- 优点。
- 成本和风险。
- 选择或拒绝原因。

当用户要求 ADR，或决策范围窄但影响长期存在时，使用 ADR 形式。

### 4. 编写技术方案

除非仓库已有更强的本地模板，否则使用以下结构：

```markdown
# {标题} 技术方案

## 1. 背景

## 2. 目标与非目标

## 3. 当前系统现状

## 4. 方案概览

## 5. 详细设计

### 5.1 模块边界

### 5.2 数据模型

### 5.3 API / 接口

### 5.4 核心流程

### 5.5 权限、安全与隐私

### 5.6 错误处理与降级

### 5.7 可观测性

## 6. 备选方案

## 7. 迁移与发布计划

## 8. 测试与验收

## 9. 风险与应对

## 10. 实施任务拆分

## 11. 待确认问题
```

小变更可以合并空小节。迁移类方案应重点覆盖兼容性、回填、回滚、监控和数据校验。

### 5. 必要时添加图表

当架构图、时序图、状态图或数据流图能帮助理解方案时，使用 Mermaid。图表应贴近解释它的章节。

### 6. 让计划可执行

实施章节必须包含：

- 有顺序的阶段。
- 预计要修改的文件或模块。
- 需要新增或更新的测试。
- 验证命令。
- 生产行为变化时的发布和回滚步骤。

避免“更新后端”这类模糊任务，优先写成具体、可评审的步骤。

### 7. 最终回复

写完文档后，总结：

- 文件路径。
- 选定方案。
- 主要风险或待确认问题。
- 已执行的验证。

除非确实已经修改了代码，否则不要声称实现已完成。
