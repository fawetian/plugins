# 智能体执行纪律

这条规则定义 AI 编码智能体在非平凡工程任务中的基础行为约束。

## 目的

用这条规则减少常见的编码智能体错误：静默假设、过度实现、无关改动，以及缺少有效验证闭环。

简单机械任务不需要重流程。只要任务存在歧义、行为风险或多文件影响，就应遵循下面的执行纪律。

## 核心规则

### 1. 编辑前暴露不确定性

- 在行动前说明关键假设。
- 多种理解会导致不同实现时，先询问；如果继续执行，应选择保守路径并说明理由。
- 明确指出重要权衡，不要静默替用户做选择。
- 当请求方案过于复杂、风险过高或偏离目标时，应提出异议并给出更小的替代路径。

### 2. 保持实现最小

- 只实现用户要求的内容。
- 不添加推测性的功能、配置项、扩展点或抽象层。
- 除非代码库已有惯例或复杂度确实需要，否则优先使用直接代码，而不是引入框架或依赖。
- 如果实现规模明显大于问题本身，应先简化，再交付。

### 3. 保持改动收窄

- 只触碰能追溯到用户请求的文件和代码行。
- 匹配现有的局部风格、命名、格式和模块边界。
- 不因为相邻代码“看起来可以改进”就顺手重构。
- 只移除本次改动造成的废弃代码。
- 发现无关死代码或缺陷时，单独说明，不顺手清理。

### 4. 从可验证结果出发

- 将请求转化为具体成功条件。
- 修 bug 时，优先先复现问题或写失败测试，再修复。
- 重构时，在可行情况下验证改动前后的行为一致。
- 多步骤任务中，每一步都要对应一个验证检查。
- 相关检查未运行前不要标记完成；无法运行时要明确说明原因。

## 完成检查清单

- [ ] 关键假设和权衡已经说明。
- [ ] 每一行改动都有能对应到用户请求的理由。
- [ ] 没有添加未要求的功能、抽象、依赖或大范围清理。
- [ ] 相关测试、构建、lint、截图或手工检查已经运行，或已说明不可运行原因。
